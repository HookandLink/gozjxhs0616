사용자가 이 스킬을 부를 때 함께 적은 내용을 확인한다.
B번호(B0, B1, …)가 없으면 [설계 모드], 있으면 [구현 모드]로 동작한다. 두 번째 단어가 있으면 담당자 이름으로 쓴다.

## [설계 모드] 리드 터미널
1. `docs/01_정리.md`, `docs/02_이해.md`를 읽는다.
2. 이 스킬 폴더의 `references/BOTTLENECKS_TEMPLATE.md` 구조로 `docs/BOTTLENECKS.md`(SSOT)를 만든다. 이미 있으면 덮어쓰지 말고 사용자에게 알린다.
3. 프로젝트를 입력→출력 흐름 순서의 병목으로 나눈다.
   - B0은 항상 '기본 제출본': 가장 단순한 방법으로 처음부터 끝까지 돌아가는 버전. 최우선.
   - 병목 하나 = 파일 하나(`src/b#_이름.py`). 팀원끼리 같은 파일을 고치지 않게 나눈다.
   - 상태표에 의존 관계를 적는다.
4. 병목마다 작성한다.
   - 핵심 제한사항 (시간·메모리·데이터 품질·규칙 등)
   - 아이디어 A, B 각각: 장점 / 단점 / 해결 가능 여부 / 치명적 문제(1절 기준 번호로 표시)
   - 결정: A, B, A+B 중 더 좋은 것. 둘 다 치명적이면 상태를 '치명적'으로 둔다.
   - 근거: 왜 이걸로 했는지 한 줄
5. 인터페이스 계약(2절)을 확정한다: 병목 사이에 주고받는 데이터의 컬럼·타입·shape. 팀원들이 서로를 기다리지 않고 동시에 만들 수 있게 하는 핵심이다.
6. 채점 재현: `docs/01_정리.md`의 평가지표를 계산하는 `eval/score.py`와 검증용 데이터 분할 방법을 만든다.
7. `src/`에 병목별 뼈대 파일(계약에 맞는 함수 이름과 입출력만)을 만든다.
8. 사용자에게 보고한다: 병목 표, 동시에 진행 가능한 병목, 터미널 배치 추천(예: 터미널2 → `$qudahr B0`, 터미널3 → `$qudahr B1`).

## [구현 모드] 팀원 터미널 (예: $qudahr B2)
1. `docs/BOTTLENECKS.md`를 읽고 해당 병목의 상태를 확인한다.
   - '진행중'인데 담당이 다르면 멈추고 사용자에게 알린다.
   - '치명적'이면 구현하지 말고 `$cnrk B#`을 안내한다.
   - 의존하는 병목이 미완료면, 인터페이스 계약에 맞는 작은 가짜 입력으로 먼저 개발한다.
2. 상태표의 자기 행을 수정한다: 담당 = 이름(없으면 `T-B#`), 상태 = '진행중'. 로그 한 줄.
3. 결정된 방식대로 사용자에게 묻지 않고 바로 구현한다. 자기 병목 파일만 수정한다.
4. 구현 중 설계를 바꿔야 하면, 코드보다 먼저 SSOT 해당 병목에 변경 내용과 근거 한 줄을 적는다.
   새로운 치명적 문제를 발견하면 상태를 '치명적'으로 바꾸고 이유를 적은 뒤 멈추고 `$cnrk B#`을 안내한다.
5. 완료 시: 상태 = '구현완료', 로그 한 줄, 사용자에게 `$xptmxm B#` 안내.
